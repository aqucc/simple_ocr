# ラベルOCR（ブラウザ完結・単一HTML）

家電などの製品ラベル（型番・製造番号のシール）をスマホで撮影し、**WebAssembly でブラウザ内ローカルOCR**（**PaddleOCR + ONNX Runtime Web に一本化**。Tesseract.js は廃止）して文字を抽出・編集し、写真とテキストを **IndexedDB** に保存する PoC アプリです。サーバーへ画像を送信しません。すべて 1 つの `index.html` で動作します。

- UI は日本語。iPhone SE3 の Safari と、デスクトップの主要ブラウザで動作します。
- 保存した記録は**保存日でグループ化**して一覧表示し、**月カレンダー**で日付を絞り込めます。

## これは何か / 主な機能

- **画像の入力（3通り）**
  - 「カメラで撮影」: `<input type="file" accept="image/*" capture="environment">`
  - 「画像を選択」: 端末内の画像ファイルを選択
  - 「クリップボードから貼り付け」: `navigator.clipboard.read()`。未対応・拒否時は日本語エラーを表示。ページ上で `Ctrl/Cmd+V`（paste イベント）にも対応。
- **読み取り範囲の指定（切り抜きGUI）**: 画像読み込み後、写真の上で枠をドラッグ（移動・四隅ハンドルでリサイズ、タッチ/マウス両対応）して読み取り範囲を指定できます。「この範囲を読み取る」「全体を読み取る」「やり直す」、結果画面からは「範囲を選び直す」が使えます。**読みたい行だけを枠で囲むのが精度向上の最重要ポイント**です。
- **エンジンの使い分け（自動）**: すべて PaddleOCR + ONNX Runtime Web。Tesseract は廃止しました。

  | モード × 経路 | エンジン |
  | --- | --- |
  | 英数字(型番向け) × 範囲指定 | **PaddleOCR PP-OCRv4**（認識モデル、rec のみ） |
  | 英数字(型番向け) × 全体 | **PaddleOCR PP-OCRv4**（DBNet 文字検出 → 認識） |
  | 日本語+英数字 × 範囲指定 | **PaddleOCR PP-OCRv3 japan**（認識モデル、rec のみ） |
  | 日本語+英数字 × 全体 | **PaddleOCR**（DBNet 文字検出 → PP-OCRv3 japan 認識） |

  **範囲指定（切り抜き）経路**は「人間の範囲指定＝文字検出」とみなし、検出モデル（DBNet）を省いて**認識モデルのみ**を実行します。範囲内が複数行の場合は水平射影プロファイルで行分割して1行ずつ認識します。**「全体を読み取る」経路**は、まず DBNet 検出モデルで画像内の各テキスト行の枠を求め（下記「文字検出」）、各枠を切り出して同じ認識パイプラインに通し、読み順（上→下、行内は左→右）に連結します。検出が0件のときは画像全体を1つの切り抜きとして扱うフォールバックがあり、行き止まりにはなりません。英数字モードの辞書は中国語+ASCII、日本語モードは japan 辞書（4,399字＋空白）です。
- **文字検出（DBNet / PP-OCRv4 det、OpenCVなし）**: 「全体を読み取る」で使う検出は、画像の長辺を960px以下（各辺を32の倍数に丸め）へ縮小し、ImageNet の平均/標準偏差（RGB `(0.485,0.456,0.406)`/`(0.229,0.224,0.225)`）で正規化して det モデルへ入力、出力の確率マップを **しきい値0.3** で二値化します。二値マスクを**既存のフラッドフィル（4連結）で連結成分に分解**し、平均確率 ≥ 0.5・面積 ≥ 9 の成分だけを残して各成分の軸並行バウンディングボックスを取り、`距離 = 面積 × 1.6 ÷ 周長` で外側へ拡張（unclip）してから元画像座標へ戻します。ラベルはほぼ水平（微小な傾きは上流の自動傾き補正が処理）なので軸並行の枠で十分です。
  - **単語レベルの自動分割**: 各行をさらに列方向のインク・プロファイル（グレースケール＋大津の二値化）で走査し、単語間の空白（**英数字はギャップ長 ≥ 行高の45%**、最低3px）を検出して**単語ごとに個別の枠を描いたのと同じ効果**を得ます（文字間のカーニングはこのしきい値を超えないため分割されません）。各単語は自身のインク行に応じて上下も詰め直し（余白15%を残してクランプ）、48px高さへの正規化後に文字がより大きく写るようにしてから個別に認識・信頼度判定（**スコア0.5未満、または英数字モードで非ASCIIストリップ後に空の単語は破棄**、行内の他の単語は生かす）を行い、生き残った単語を空白1つで連結します。分割数が多すぎる場合（24個超、バーコードや模様の可能性が高い）は分割せず行全体を一括認識します。**日本語モード**では日本語に語間スペースが無いため、しきい値を大きく緩めて（行高の110%）「定格 / 100V / 50Hz / 1.5A」のように明確に離れたフィールドだけを分割し、連続する漢字かな（例: `東京都千代田区1-2-3`）は分割しません。分割せず行全体を認識する場合は、まず**左右の余白列を詰めて**（`trimLineToInk`）から48px高さへ正規化します。余白の多い横長の切り抜き（「全体を読み取る」や広めの範囲指定）をそのまま横方向に潰すと文字が欠ける（例: `50Hz` の `z` が落ちる）ため、インク範囲だけを縮小対象にします。以上により (a) このモデルが単語間スペースを安定して出力しないケース（例:「MADE IN JAPAN」が「MADEINJAPAN」に潰れる）を回避し、(b) バーコードの縞模様に隣接する型番/シリアル等の数字だけを個別に救出できます（下記）。
  - **バーコードに強い行検出**: 行分割（水平射影プロファイル）のしきい値は、従来は画像内で最もインクの多い行の12%を基準にしていましたが、これだとバーコードの縞模様の行が突出して基準を釣り上げてしまい、その下に印字された薄い数字の行が背景として無視される（またはバーコードの行と数字の行が1つに結合され、結合後の一括デコードがスコア0.5未満のゲートで丸ごと落とされる）問題がありました。今は、緩い絶対フロアだけで見つけた「候補ブロック」ごとのピーク値のうち**最も弱いブロックのピーク**を基準にしきい値を決めます（バーコードのような単一の密なブロックが基準を釣り上げられないようにする一方、候補が1つしかない通常の複数行ラベルでは従来と同じ挙動になります）。
- **前処理（canvas）**: PaddleOCR はカラー入力（PP-OCR 系は非二値化入力が前提）なので、認識モデルには切り抜き（傾き補正・台形補正済み）をそのまま渡します。認識前の正規化は `(x/255 − 0.5)/0.5`・BGR チャンネル順・高さ48px固定（japan モデルは内部の reshape が高さ48を要求するため 48 に固定）。行分割・単語分割・左右余白詰めは上記の純粋な canvas 処理で行い、Tesseract 時代の二値化（局所適応しきい値・デスペックル）は不要になったため削除しました。傾き補正（±12°の自動デスキュー）・台形補正（4点ホモグラフィ）は引き続き純JSで実装しています。
- **信頼度によるノイズ除去（ハルシネーション対策）**: 背景ノイズだけの領域を文字と誤認識しても結果に出さないよう、認識は行ごとの CTC 貪欲デコードで採用した各文字の確信度（非空白・非重複ステップの argmax 確率の平均、モデル出力は既に softmax 済み）が **0.5 未満の単語/行を破棄**し、全行破棄なら結果は空文字列にします。英数字モードでは辞書が中国語+ASCII であるため、残った行からさらに**非ASCII文字を除去**（連続する空白は1つに畳み込み、結果が空になった行は破棄）します。日本語モードでは非ASCIIストリップは行わず（かな・漢字を残すため）、全角→半角正規化（下記）のみを適用します。
- **単語フィルタ（ハイブリッド・トークン分類器によるノイズ除去）**: 信頼度による足切りをすり抜けるノイズもあります。認証マーク・ロゴ（PSE、丸囲みのR ®、角囲みの検印など）の中の文字が、孤立した記号・単独のCJK文字・意味のない短いトークンとして誤認識されるケースです。詳細は下記「単語フィルタの設計」を参照。**例外（EANバーコードの先頭1桁）**: 単独の英数字トークンは通常2文字未満だと破棄されますが、その行に数字が合計6桁以上含まれる場合に限り、単独の数字1文字トークンは破棄されません（例:「4 901234 567894」の先頭の「4」）。EAN/UPCバーコードの慣習的な印字（先頭1桁＋6桁×2グループ）を想定した狭い例外で、それ以外では2文字以上ルールを緩めません。結果画面のテキストエリア上部に「単語フィルタ」トグル（既定 ON、`localStorage` に記憶）があり、タップでフィルタ後/フィルタ前（生の認識結果）を切り替えられます。フィルタで全行が消えてしまった場合は自動的に生テキストへフォールバックし、トグルは OFF 表示になります（結果が悪化しないため）。**注意**: トグルはテキストエリアの内容を丸ごと置き換えます。手動編集後にトグルを押すと編集内容は失われます（シンプルさを優先した仕様）。
- **認識モード（撮影画面・撮影ボタンの上）**: 2つのセグメントボタンから選択でき、選択は `localStorage` に保存され次回起動時も復元されます。
  - 「英数字(型番向け)」（既定）: PaddleOCR PP-OCRv4。初回のみエンジン+モデル（合計約22MB: ONNX Runtime WASM 約11.0MB + 認識モデル約10.8MB。「全体を読み取る」では加えて DBNet 検出モデル約4.7MB）をダウンロードします。
  - 「日本語+英数字」: PaddleOCR **PP-OCRv3 japan 認識モデル**（**自己ホスト** `models/japan_rec.onnx`＋辞書 `models/japan_dict.txt`）。和文に加え、住所の `1-2-3` や型番の半角ASCII数字もそのまま読み取れます（例: `東京都千代田区1-2-3` の `1-2-3`、`定格 100V 50Hz 1.5A` の数値、`型番たしかめ 12-34` のかな＋数字がいずれも保持されます）。モデルは `new URL("models/japan_rec.onnx", document.baseURI)` で**ドキュメント相対**に解決するため GitHub Pages のサブパス配信 `/simple_ocr/models` でも動作します。初回切替時にモデル（約10MB）をダウンロードするため時間がかかる旨のヒントを表示します。
    - **既知の弱点（japan 認識モデル）**: 漢字に隣接した孤立した大文字ラテン（例: `型番 KX` の `X`）をカタカナ `メ` と誤読したり、単位の `V`/`Hz` を小文字 `v`・大文字 `Z` で出すことがあります。数字・漢字・かなの認識は良好で、ユースケース（住所・数値・かな・数字入り型番）はカバーします。
  - **全角→半角の正規化（日本語モード）**: 保存対象が型番・住所であるため、日本語モードの認識結果は**単語フィルタの前に**全角ASCII（０-９Ａ-Ｚａ-ｚ）・全角ハイフン `－`・各種ダッシュ／マイナス記号・全角スペースを半角へ折り畳みます（カタカナ長音符 `ー`（U+30FC）はいずれの範囲にも含めず保持）。これにより住所の `1-2-3` や `KX-1234` が素の ASCII で保存され、数字トークンが単語フィルタの型番ルールに合致します。
  - **注意（`file://` 直開き）**: 自己ホストの japan モデル・辞書は `fetch` で取得するため、`file://` で開くと（オリジンが無く）取得に失敗します。OCR には HTTP(S) 配信が必要です（他の CDN 資産と同じ制約）。
- **OCR（進捗表示）**: 進捗バーとステータス（例: 認識中…・文字領域を検出中…）を表示。認識セッションはモードごとにキャッシュし、モード切替時に**非アクティブなモードの認識モデルを解放**してメモリを抑えます（iPhone 対策）。検出モデルは両モードで共有。ORT／モデルの読み込みに失敗した場合は（Tesseract フォールバックが無くなったため）明確な日本語エラーを表示し、行き止まりにしません。ONNX Runtime は**シングルスレッド**設定（GitHub Pages は COOP/COEP ヘッダを送らないため `SharedArrayBuffer` が使えない）で、SIMD 有効・プロキシワーカー無効です。結果画面には使用エンジン名（例: `PaddleOCR (PP-OCRv4)` / `PaddleOCR (PP-OCRv3 · japan)`）を表示します。
- **結果画面**: 撮影画像プレビュー、認識テキストの編集用 `<textarea>`、信頼度表示、「保存する」/「破棄」。
- **保存（IndexedDB / ライブラリなし）**: `{ id, createdAt(ISO), dateKey(YYYY-MM-DD ローカル), text, imageDataUrl(最長800pxのJPEG, 画質0.7) }`
- **一覧**: 保存日ごと（新しい日付が上）にサムネイル・テキスト・時刻・操作ボタン（コピー・再読み取りの主要行、編集・削除の第二行の2段構成。削除は危険色で他と誤タップしにくい配置）。「削除」は `window.confirm` で確認します。**サムネイルをタップするとライトボックス（全画面オーバーレイ）で拡大表示**され、どこかをタップすると閉じます。「再読み取り」は保存済みの画像を撮影フローに読み込み直し、範囲選択からやり直せます（保存画像は最長800pxに縮小したJPEGのため、元の撮影解像度ではなくその解像度での再認識になります）。
- **記録テキストの編集**: 「編集」をタップするとそのカードだけがテキストエリアに切り替わり、既存テキストが入った状態で「保存」/「キャンセル」が表示されます。**同時に編集できる記録は1件のみ**（別の記録で「編集」を押すと、前の記録は未保存の変更を破棄して自動的に編集モードを終了します）。編集中はそのカードの「コピー」「再読み取り」「削除」を表示せず誤タップを防ぎます。「保存」は同じ `id`・`createdAt`・`dateKey` のまま `text` だけを更新し、一覧を更新して「更新しました」というトーストを表示します。「キャンセル」は変更を破棄します。
- **カレンダー**: 月グリッド（曜日 日月火水木金土）、前後月の切替、記録がある日にバッジ、日タップで一覧を絞り込み、「すべて表示」で解除。

## 開く / 使い方

- **クリップボード読み取り（貼り付けボタン）を使うには HTTP(S) 配信が必要**です（`navigator.clipboard` は secure context 前提）。ローカルでは例えば次のいずれか:
  - `python3 -m http.server 8000` の後、`http://localhost:8000/index.html`
  - `node tools/verify.mjs` は検証用の簡易サーバーも起動します（検証専用）。
- **カメラ撮影・画像選択**だけなら `file://` で直接 `index.html` を開いても動作します（ただし CDN 取得のためオンラインが必要）。
- 依存（Vue / ONNX Runtime Web / PP-OCRv4 検出・認識モデル等）は **cdn.jsdelivr.net から都度ダウンロード**します。日本語の認識モデル・辞書（`japan_rec.onnx` / `japan_dict.txt`）は**リポジトリ同梱の `models/` を同一オリジンから配信**します。いずれも初回 OCR 時に数〜十数MBを取得するため、初回は時間がかかります（ブラウザにキャッシュされます）。

### iPhone（SE3 / Safari）での注意

- 「カメラで撮影」はカメラ／写真ライブラリの選択ダイアログが出ます。ラベルを**大きく・明るく・正面から**撮ると精度が上がります。
- EXIF の向きは Safari が自動補正します（本アプリは `createImageBitmap({ imageOrientation: 'from-image' })`、非対応時は `<img>` 経由で描画）。EXIF 解析ライブラリは同梱していません。
- クリップボード画像の読み取りはユーザー操作＋許可が必要で、機種・iOS バージョンにより挙動が異なります。未対応時はエラーメッセージを表示します。
- 画面幅 375px を基準にしたモバイル優先デザイン。タップ領域は最小 44px・隙間 8px 以上を確保し、記録カードの操作ボタンは2段組、結果画面は「保存する」を単独の全幅プライマリボタンにして「破棄」と誤タップしないよう配置しています。

## セキュリティ（CSP）

`index.html` は厳格な CSP を `<meta http-equiv="Content-Security-Policy">` で指定します。`'unsafe-inline'` / `'unsafe-eval'` は使いません。インラインの `<script>` と `<style>` は **sha256 ハッシュ**で許可します（WASM のために `'wasm-unsafe-eval'` のみ許可）。

現在のポリシー:

```
default-src 'none';
script-src 'sha256-…(inline script)…' https://cdn.jsdelivr.net 'wasm-unsafe-eval';
style-src 'sha256-…(inline style)…';
img-src 'self' blob: data:;
connect-src 'self' https://cdn.jsdelivr.net data:;
worker-src blob:;
base-uri 'none';
form-action 'none'
```

- `script-src`: インラインscript（ハッシュ）、Vue 本体、onnxruntime-web の遅延ロード（`<script>` 挿入）と内部の動的 `import()`（いずれも jsdelivr）、WASM 実行（`wasm-unsafe-eval`）。
- `worker-src blob:`: onnxruntime-web が内部で Blob URL の Worker を使う可能性に備えて許可しています。
- `connect-src`: `'self'` は**自己ホストの日本語モデル・辞書**（同一オリジンの `models/japan_rec.onnx` / `models/japan_dict.txt`。`fetch` で取得）のために追加しました。`https://cdn.jsdelivr.net` は ONNX Runtime の `.wasm` / PP-OCRv4 検出・認識モデル・辞書、単語フィルタの英単語リスト（`word-list` の `words.txt`）の取得に、`data:` は WASM の `data:` URI 取得に使います（`tools/verify.mjs` で CSP 違反ゼロを確認済み）。
- `img-src`: 保存画像・プレビュー（`data:` / `blob:`）。

### CSP ハッシュの再生成

`index.html` のインライン `<script>` か `<style>` を編集したら、必ず以下を実行してハッシュを更新してください:

```
node tools/update_csp_hash.mjs
```

`tools/update_csp_hash.mjs`（依存なしの素の Node）が、インライン `<script>` と `<style>` の sha256 を計算し、CSP メタタグ内の該当トークンを書き換えます。

## 単語フィルタの設計（ハイブリッド・トークン分類器）

信頼度による足切り（上記）をすり抜けるノイズの典型例は、認証マーク・ロゴの中の文字です。PSE マーク、丸囲みの ® / Ⓡ、角囲みの検印（例: ㊞）などは、OCR エンジンには「文字」として写るため信頼度は高く出ることがあり、孤立した記号・単独のCJK文字・意味のない短いトークンとして結果に混入します。

**なぜ「辞書に載っている単語だけを残す」方式にしなかったか**: このアプリの核心的な価値は型番・製造番号（例: `KX-1234AB`、`5X-98765`）を読み取ることですが、これらは英単語ではありません。純粋な辞書フィルタは英単語しか残さないため、**アプリの存在意義そのものを消してしまいます**。そこで、次のいずれかに当てはまるトークンだけを残す**ハイブリッド分類器**にしました:

1. **英単語**: 小文字化して辞書（下記）に載っている（2文字以上、末尾の句読点は除いて判定）。
2. **型番らしい文字列**: `/^[A-Za-z0-9][A-Za-z0-9\-\/.:#+]*$/` に一致し、かつ数字を1文字以上含み、2文字以上（`KX-1234AB` / `5X-98765` / `100-240V` などを保持）。
3. **単位付きの数値**: `/^\d+(\.\d+)?(V|W|A|VA|Hz|kHz|mA|Ah|kg|g|L|mm|cm|°C)\.?$/i`。
4. **ラベル定型の略語のホワイトリスト**: `MODEL`, `MODELE`, `TYPE`, `SN`, `S/N`, `P/N`, `NO`, `NO.`, `LOT`, `REF`, `AC`, `DC`, `PSE`, `CE`, `FCC`, `MADE`, `IN`。

上記いずれにも当てはまらない（句読点のみ、意味のない短い記号列など）トークンは削除します。

**記号ノイズの除去**: 丸囲み英数字（U+2460–24FF）、丸囲み/角囲みCJK（U+3200–32FF、U+3300–33FF）、Letterlike Symbols（U+2100–214F、™など）、Geometric Shapes（U+25A0–25FF）、Misc Symbols/Dingbats（U+2600–27BF）、および ®©™§※ を行ごとに一括除去してから、CJK文字とASCIIトークンに分けて上記の判定を行います。

**CJK（日本語）の扱い**: 行内でCJK文字どうしの間にある空白は詰めます（スペースを取り除く、ユーザー要望どおり）。そのうえでCJKの連続（ラン）を1単位とし、**ランの長さが2文字以上なら保持**（孤立した単独の漢字・かなは、囲み文字の誤読の典型パターンとして削除）。ラベル語彙の埋め込み辞書（型番・品番・型式・製造番号・定格・電圧・株式会社・日本製・取扱説明書・注意・警告など、appliance/label 向けに約80語）に含まれる／を含むランも保持します。

**既知の弱点**: ランの長さのみで判定するため、無関係な2文字のノイズ（例: ノイズ由来の「をッ」のような2文字が偶然隣接した場合）は誤って保持されることがあります。これは長さ基準というヒューリスティックの性質上の限界であり、`tools/verify.mjs` のノイズテスト（日本語モードの PaddleOCR 経路）の許容閾値内に収まっています。

### 英単語リスト（辞書）

npm パッケージ [`word-list`](https://github.com/sindresorhus/word-list)（Sindre Sorhus 作、MIT）の `words.txt` を使用します。

- **固定バージョン・URL**: `word-list@4.1.0` → `https://cdn.jsdelivr.net/npm/word-list@4.1.0/words.txt`
- **サイズ**（npm tarball から実測）: 274,136 語、生ファイル 2,805,374 bytes（約2.68MB）、**gzip 転送時 約697KB**（713,721 bytes、`gzip -9` で実測）。
- **遅延ロード**: 単語フィルタを初回使用するタイミング（＝デフォルトONのため実質的に初回のOCR結果を表示する直前）で `fetch()` → `split("\n")` → 小文字化して `Set` に格納し、モジュールスコープの変数にキャッシュします。取得中は既存の進捗表示に「辞書を読み込み中…」を短く表示します。
- **取得失敗時のフォールバック**: 例外を `console.warn` するだけで、ユーザーにはエラーを出さず、辞書チェックが常に `false` を返す「パターンのみモード」で動作を継続します（型番・単位・略語ホワイトリストの判定は引き続き機能するため、行き止まりになりません）。
- **JS の `Set`（WASMではない）を使う理由**: 27万語程度の完全一致ルックアップは `Set.has()` で O(1) かつ数MB規模のメモリで十分高速に処理でき、WebAssembly 化するメリット（バイナリサーチ木の圧縮やSIMD走査など）が要求される規模ではありません。本アプリの他の重い処理（OCR推論）はすでにWASMを使っており、この用途にまでWASM化する必要性は低いと判断しました。

## 検証（自動テスト）


Playwright + Chromium（プリインストール）で以下を確認します:

1. ローカル HTTP でリポジトリを配信し `index.html` を開く。
2. コンソール／ページエラーを収集し、**CSP 違反・JS エラーがあれば失敗**。

4. 「範囲を選び直す」→「全体を読み取る」→ **PaddleOCR の DBNet 検出＋認識**経路でも同テキストに一致し、エンジン表示が PaddleOCR であることを検証。
5. 保存 → 一覧へ切替 → 今日の日付見出しに記録が出る／カレンダーにバッジが付く → リロード後も記録が残る（IndexedDB 永続化）ことを検証。続けて「編集」→ テキストエリアに既存テキストが入っていること／他の操作ボタンが非表示になることを確認 → テキストを変更して「保存」→ 一覧の表示が更新されること → リロード後も編集後のテキストが残る（IndexedDB 永続化）ことを検証。
6. 「日本語+英数字」モードに切替 → 初回ダウンロードのヒント（MBサイズ表示）が出ることを確認 → ラベル画像を注入 → 枠を拡大して「この範囲を読み取る」（jpn は PaddleOCR japan 認識モデル）。実行コンテナに CJK フォントがあれば `品番 AB-1234`（漢字＋ラテン＋数字。エンジン表示が PaddleOCR であることも確認）、なければ ASCII のみの画像で OCR が成功することを検証。続けて CJK フォントがある場合の**受け入れゲート**として、`東京都千代田区1-2-3`（漢字＋埋め込み数字が正確に読めること）、`定格 100V 50Hz 1.5A`（数値・単位が残ること。単位の大小文字は上記の既知の弱点があるため大小無視で判定）、**かなテスト** `型番たしかめ 12-34`（ひらがなが**ASCIIストリップされず残る**こと＋`12-34` が正確）を検証します。CSP 違反ゼロも同様に確認。
7. **ノイズ耐性テスト（ハルシネーション対策の受け入れゲート）**: 斜めのグレーグラデーション背景＋約800個の低コントラストな砂嵐状ノイズ（点・短い線）＋軽いビネットの上に同じラベル文字を描画した画像（決定論的シード付き乱数で再現可能）を、切り抜き→英数字モードと切り抜き→日本語モードの両方（いずれも PaddleOCR）に流し、期待文字列の正規表現一致に加えて「期待される文字列に含まれない英数字・CJK文字数（＝ハルシネーションの目安）」が英数字は3文字以下、日本語は6文字以下であることを検証します。この中で**単語フィルタのトグル機構**（ON→OFFでテキストエリアの内容が生の認識結果に切り替わり、生テキストのガーベジ数がフィルタ後以上であること）も検証します。
8. **単語フィルタ（デコイ認証マーク画像）テスト**: 丸囲みの「R」・角囲みの漢字「検」（IPAGothic）・三角形の記号・`MODEL: KX-1234AB` / `S/N 5X-98765` / 実在の英単語「MADE」「JAPAN」を描画したラベル画像を、切り抜き→英数字モード（PaddleOCR）経路に流し、フィルタ後のテキストに `KX-1234AB` / `98765` / `MADE` / `JAPAN` が含まれること、**単独1文字のトークンが一切残っていないこと**、ガーベジ数が2以下であることを検証します（PaddleOCR の認識経路は非ASCII文字を既存の仕組みで除去済みのため、角囲み漢字は本テスト時点で単語フィルタに到達する前に消えます。CJKのラン長ルールは日本語モードのテスト群で別途検証されます）。
9. **単語レベル分割（受け入れテスト）**: `MODEL: KX-1234AB` / `S/N 5X-98765` に加え、単語間隔を広く取ったモノスペースの1行 `MADE     IN     JAPAN` を描画したラベル画像を、切り抜き→英数字モード（PaddleOCR）経路に流し、認識結果の**同じ出力行に** `MADE` と `JAPAN` が含まれること（`IN` も含めた `MADE IN JAPAN` 全体が復元されるのが理想だが、`IN` は認識の揺れで欠けても許容）を検証します。単語ごとに個別の枠で切り出して認識することで、行内スペースをCTCが安定して出力しない問題を回避できていることの実証です。
10. **バーコード隣接の数字（受け入れテスト）**: ランダム幅の縦縞40本・高さ約60px・幅の約70%を占めるバーコード風のブロックの直下に、それ以外は何も描かずEAN風の数字行 `4     901234     567894`（先頭1桁＋6桁×2グループ、単語ごとに広い間隔）を描画した画像を、切り抜き→英数字モード（PaddleOCR）経路に流し、認識結果に `901234` と `567894`、および**単独の数字トークン `4`**（単語フィルタのEAN例外）が含まれること、ガーベジ数が2以下（バーコードの縞模様自体からトークンが生き残っていないこと）を検証します。バーコードに強い行検出と単語単位の信頼度判定の両方がないと、この数字はバーコードの行に埋もれるか、行全体が道連れで棄却されて消えていました。

## 既知の制限（PoC）

- **オンライン必須**: Vue / ONNX Runtime WASM / PP-OCRv4 検出・認識モデル（初回約22〜27MB）は CDN から取得します。日本語の認識モデル・辞書（約10MB）はリポジトリ同梱の同一オリジン配信ですが、いずれもネットワーク越しの取得（初回はブラウザにキャッシュ）で、`file://` 直開きではモデルの `fetch` が失敗します。完全オフライン化には CDN 資産も自前ホスティングが必要です。
- **日本語認識モデルの弱点**: PP-OCRv3 japan モデルは、漢字に隣接した孤立した大文字ラテン（例: `型番 KX` の `X`→`メ`）や単位の大小文字（`V`→`v`、`Hz`→`Hz`/`HZ` の揺れ）で誤りが出ることがあります。数字・漢字・かなの認識は良好で、住所・数値・かな・数字入り型番といった主要ユースケースはカバーします（結果はテキストボックスで編集可能）。
- 英数字モードの辞書は中国語+ASCII のため、まれに漢字ノイズが混じることがあります（非ASCIIストリップで大半は除去）。**大きく斜めのラベル**は自動デスキュー（±12°）と台形補正で補いますが、範囲がずれると精度が落ちます。範囲指定で読みたい行だけを囲むのが最も効果的です。「全体を読み取る」では DBNet が各行を検出しますが、極端な低コントラスト・過密レイアウトでは検出漏れが起きえます（その場合は範囲指定を推奨）。
- **保存容量**: 画像は最長800px/JPEG 0.7 に縮小して保存しますが、IndexedDB の容量はブラウザ依存。多数保存すると上限に達する可能性があります。エクスポート機能はありません。
- **クリップボード読み取り**は secure context（HTTPS/localhost）とユーザー許可が必要で、対応状況はブラウザ依存。
- **保存画像の EXIF**は描画時に向きのみ反映。位置情報などのメタデータは保持しません。
- カレンダーは単月表示のみ。テキストの編集（保存済み記録の `text` 上書き）はできますが、検索・タグ付けなどの管理機能はありません。
- 検証は Chromium のみ（Playwright）。実機 Safari での自動テストは含みません。
- **単語フィルタの既知の弱点**:
  - CJKランの長さのみで判定するため、無関係な2文字以上のノイズ（例: たまたま隣接した2文字の空似のかな）を誤って保持することがあります。
  - 英語辞書は一般的な単語リストで、固有名詞は限定的にしか含まれません（"japan" 等の一部の国名は含まれますが、すべての固有名詞・ブランド名を網羅しません）。該当しない単語は型番らしいパターンやホワイトリストに一致しない限り削除されます。
  - トグルはテキストエリアの内容を丸ごとフィルタ後/フィルタ前のテキストで上書きします。手動編集後にトグルを押すと編集内容は失われます。
  - 辞書取得に失敗した場合は「パターンのみモード」（型番・単位・略語ホワイトリストのみ）で動作するため、辞書が使えない間は一般英単語（例: 実在するが型番にもホワイトリストにも該当しない単語）が削除されることがあります。
- **単語レベル分割（PaddleOCR経路）の既知の弱点**:
  - 列方向のインク・プロファイルによる分割のため、単語間隔が狭い書体・詰め組み・筆記体風フォントでは単語同士が結合したまま分割されないことがあります（従来どおり行全体で一括認識されるだけで、悪化はしません）。
  - 逆に文字内に大きな空白があるフォント・字体（例: 装飾書体）では1単語が複数に分割される可能性があります。分割数が24を超える行（バーコード・模様の可能性が高い）は分割せず行全体を一括認識するフォールバックがありますが、それ未満で誤分割された場合は各断片が個別に信頼度判定されるため、本来1単語のテキストが欠落することがあります。
  - EAN単独数字の例外はその行に数字が合計6桁以上ある場合のみ働くため、6桁未満の短い数字コードの単独1文字トークンは引き続き削除されます。
